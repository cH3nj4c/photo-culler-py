## 启动失败报错排查（用户反馈）

用户发来截图：启动弹出「程序启动失败」，正文为
`Tkinter 界面不可用（缺少 tkinter 模块）。No module named 'numpy'`。

### 根因：解释器选错了，不是程序坏了

用户是用**系统 Python 3.14** 跑的 `app.py`。实测该环境：

| 模块 | 系统 Python 3.14 | `.venv-build` | 隔离 venv（managed 3.13.12） |
|---|---|---|---|
| tkinter | 有 | 有 | **无** |
| numpy | **无** | 有 | 有 |
| PIL | 有 | 有 | 有 |
| rawpy | **无** | 有 | 有 |
| PySide6 / vispy / OpenGL | **无** | 有（本次补齐） | 有 |

这台机器上 **tkinter 存在、numpy 不存在** 的组合只有系统 Python，所以能弹出 Tk 对话框却报 numpy 缺失。Qt 路径也因为同一个 numpy 先挂掉（`qt_ui` 先 import numpy），于是两个界面都起不来。

### 修掉的三个真问题

1. **`app.py` 的报错信息武断地把原因写成「缺少 tkinter 模块」**，而真实原因是 numpy——这条消息把排查方向完全带偏了。且 auto 模式下 Qt 侧的 ImportError 被直接丢弃，无法在最终消息里说明 GPU 界面缺什么。
   重写为 `_startup_diagnosis()`：用 `importlib.util.find_spec` **逐界面探测各自缺失的模块**（不做 import，避免拖入 PySide6 且不会半路抛错），分别列出「GPU 界面缺少 / Tkinter 界面缺少」，给出对应 pip 命令，并打印当前解释器路径。
   *为什么不能只报第一个 ImportError*：在裸 Python 里 Qt 外壳会先撞上 numpy 而不是 PySide6，于是 GPU 界面看起来只需要 numpy。
   另：`rawpy` 是**可选**依赖（`imaging.py` 里 try/except 成 None，用到时才报错），绝不能当成启动阻塞项列出来。
   顺带修正 `main()`：auto 模式回退 Tk 时往 stderr 打一行提示 + 安装命令，避免「GPU 引擎静默消失」被误认为引擎坏了。

2. **`build_exe.bat` 只在「创建 venv」时才装依赖** → 已存在的 `.venv-build`（GPU 界面出现之前建的）永远不补装 PySide6/vispy/PyOpenGL → 打出来的包**根本没有 GPU 界面**。
   实测确认：`dist/PhotoCuller/` 里 `_internal/numpy`、`PIL`、`rawpy`、`_tk_data` 都在，而 **PySide6 / vispy / OpenGL 全部不存在**。也就是说发布版一直只能跑 Tk 界面。
   改为：先 `python -c "import PySide6, vispy, OpenGL, numpy, PIL, rawpy, PyInstaller"` 校验完整性，缺了才安装；DLL 拷贝改成 `for` 循环并对缺失给出 WARNING（原来是 `copy ... >nul` 静默失败）。

3. **新增 `run.bat`**：自动在 `.venv .venv-build` 里挑一个真能跑的解释器（优先有 GPU 依赖的，其次有 numpy 的），都没有才回退 PATH 上的 `python`。README 中英双语的「使用」章节也改成先讲 `run.bat` 并明确警告不要直接 `python app.py`。

## 缩略图条「无法显示全部图片」排查

用户反馈缩略图条问题很大。照例先复现再动手，写了 `_probe_strip.py` 造 N 张照片直接量条目数/滚动范围/图标数/各处理器耗时。

### 两个真实缺陷

1. **打开大文件夹时界面硬卡 1.6–2 秒** —— 根因是 `domain.build_photo_groups()` 对**每个文件**调用 `Path.resolve()`。实测 `resolve()` 在 Windows 上是真的文件系统调用，**单次 0.965 ms**（`str()` 只要 0.00012 ms），2000 个文件就是 1.93 秒。而它被 `_handle_scan_events` 放在 **UI 线程的 16ms 轮询**里跑。
   两处修：
   - `domain.py`：把"每文件一次 resolve"改成**每目录一次**（缓存 `parent.resolve()`，再拼文件名；对普通文件结果逐字节相同）。平铺 3000 文件：**1935ms → 36ms**。
   - `qt_ui.py`：分组建到扫描线程 `work()` 里做（`scan_photo_tree` 本来就走遍所有目录），"done" 事件多带一个 `groups` 字段，UI 侧直接采用；`groups=None` 时保留 UI 线程兜底。
   实测 1500 张：`_handle_scan_events` **1619ms → 24ms**。
   注意：多子目录的场景仍要每目录一次 resolve（1000 目录 × 3 文件 = 1294ms），所以"挪到工作线程"这一半不可省。
2. **触控板/横向滚轮完全滚不动缩略图条** —— 原实现 `int(-delta / 120.0) * 96`：任何**小于一格**的增量（高精度触控板、无级滚轮）都被截断成 0；且只看 `angleDelta().y()`，横向滑动（`angleDelta().x()`）也是 0。重写为：优先用 `pixelDelta()`，否则取 `angleDelta().y() or .x()`，并用 `_wheel_remainder` 累积小数部分（避免慢速滚动被舍掉）。实测三种输入都能滚（触控板每次 +12，横向 +96，pixel +40），方向语义不变。

### 排掉的假象（重要）

- 首版探针用「**缓存数**不再增长」判断解码结束 —— 但 `THUMB_CACHE_LIMIT=110`，缓存数远早于解码完成就被上限卡住，于是探针提前收尾，报出"400 张里只有 198 张有图标、末尾 38 个空白"的**假缺陷**。改成跟踪**图标数**停止增长后，400/1500/2000 张全部 400/1500/2000 有图标。
- 隐藏窗口（`WA_DontShowOnScreen`）**不会跑 item 布局**，于是 `visualItemRect()` 返回 0 宽退化矩形、`scrollToItem()` 变成空操作（`bar.value()` 停在 0）。这看起来像"滚不到最后一张"，其实是假象。判据：重新 `setGridSize/setIconSize` 强制布局后一切正常。真正可靠的判据是 **`bar.maximum() + bar.pageSize() == 条目数 × GRID 宽`**（实测精确相等），所以回归测试断言的是这个不变量。
- 一度怀疑删除路径（`_forget_deleted` → `build_photo_groups`）也有同样的 2 秒卡顿 —— 读代码发现它的入参只是**被删组的成员**（1–2 个文件），不成立。

### 验证

- 新增 key 等价性检查（临时脚本，含**junction** 场景）：新旧实现的 `key` / `primary_id` 字符串**逐字节一致**，所以已保存的选片记录不会失效。这点必须验，key 是持久化到选片 JSON 里的。

### 缩略图条「细条」截图的确诊（用户二次反馈）

用户发来截图：打开时缩略图条是一排**等距的 1 像素竖线**（间距正确 ≈148px，内容塌缩）。这就是我上一轮在探针里看到的 0 宽矩形 —— 当时我误判成"隐藏窗口没跑布局的假象"，**这个结论是错的**。

- **根因**：`QListWidgetItem()` 既没图标又没显式 `setSizeHint()` 时，sizeHint 为空，条目被画成 **0×15 细条**。缩略图条正是这种状态：打开文件夹先建全部条目，缩略图之后才异步解出来。
- **实测对照**（`grab()` 强制真实布局后量 `visualItemRect`）：无 sizeHint 无图标 = **0×15**；无 sizeHint 有图标 = 148×116；**有 sizeHint 无图标 = 148×116**；有 sizeHint 有图标 = 148×116。
- **修复**：`_render_thumbnails` 建条目时立刻 `entry.setSizeHint(QSize(THUMB_SLOT, THUMB_PIX_HEIGHT))`。用确定性探针复现截图状态（清空 `_thumb_pil` 再重渲染，等价于"打开时还没解出来"）：150 行全部 148×116、塌缩槽位 0。
- **教训**：把 `visualItemRect` 退化归因于"隐藏窗口"是错的 —— 那只是**叠加的**测量假象，真正的原因（空 sizeHint）在真实可见窗口同样发生。两者要分开验证。

`test_gpu_ui.py` 新增 [13e]：清空 PIL 缓存后重渲染，断言每个条目的 `sizeHint()` 和 `visualItemRect()` 都是 148×116（与图标状态无关的稳定不变量）。全套 17 步通过；`test_smoke.py` 通过。

## 缩略图条滚动条遮住文件名（用户三次反馈）

- **现象**：滚动条压住每个槽位底部画的名字。
- **几何事实**（`_probe_stripgeom.py` 实测，DPR 1.25）：文件名画在 148×116 槽位像素图的 **y=100..116**（`y=6; thumb 6..94; label at y+88+6`）。条高原是写死的 `THUMB_PIX_HEIGHT + 18 = 134`，视口 118 → 只比槽位高 **2px**。样式表 `QScrollBar:horizontal { height: 10px }` + 框架实际占 15px，只要滚动条再高一点（不同样式/DPI/缩放），视口就会矮于槽位，**最先被裁掉的就是文件名**。
- **修复**：`qt_ui.PhotoCullerWindow._fit_strip_height()` —— 滚动条自身 `sizeHint()` + 滚动区 `frameWidth()`×2 作为开销（本机 14+2=16），再加上 `STRIP_NAME_GAP=8` 的呼吸空间。条高变为 140，视口 124，名字下方 **8px** 空隙。
- **两次踩坑（别再犯）**：
  1. 第一版在 `_build_ui` 里就实测 `strip.height() - viewport().height()` —— 但**窗口还没布局**，两个值都是临时的，算出 overhead=2，把条压到 126px，视口反而矮了 6px（比原 bug 更糟）。
  2. 改成 `initialize_after_show` 里实测**仍然不行**（126px）：隐藏窗口下布局依旧没就绪。
     **结论：`height() - viewport().height()` 这种"实测高度差"在布局就绪前完全不可信；要用 `horizontalScrollBar().sizeHint()` + `frameWidth()` 这种随时可取、与条高无关的量。**
- `test_gpu_ui.py` 新增 **[13f]**：断言 `viewport().height() >= 条目高度` 且空隙 ≥4px。全套 18 步通过。
- `_probe_stripgeom.py`（临时，已删）是这类几何问题的通用做法：量 `viewport().geometry()`、`visualItemRect()`、滚动条 `sizeHint()`，把名字在**控件坐标系**里的矩形和滚动条带比较。

## 打包被删除拦截 + `--self-test` 是假阳性（本轮新发现）

### 1. PyInstaller 的 COLLECT 阶段被 file-deletion shim 掐断

`build_exe.bat` 首次经 PowerShell 跑失败，日志停在：

```
INFO: Removing dir G:\...\dist\PhotoCuller
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":2401,"threshold":50,...}
```

PyInstaller 在 COLLECT 前会**递归删掉旧的 `dist/PhotoCuller/`**（2401 个文件），触发 shim 的批量删除确认阈值 → 构建中断，`dist/` 留在半成品状态。
**修法**：`build_exe.bat` 里在调用 PyInstaller 前 `set CODEBUDDY_SAFE_DELETE_ENABLED=0`（和 pip 装包时同一个开关）。已写进脚本，不用每次手动加。

### 2. `.bat` 编辑后必须复核行尾 —— 而且别在构建中途改脚本

`run.bat` 一直是 **LF-only**（49 行全是 lone LF），而它含 `for ... do ( if ... ( ... ) )` **嵌套块** —— 正是 memory 里记过的会错位崩掉的形态。已转 CRLF。

更隐蔽的一个：**在 `build_exe.bat` 正在运行时编辑它**，cmd 是边读边执行的，结果同一次运行里 PyInstaller 被跑了**两遍**，还夹一句 `'ent' 不是内部或外部命令`（我新加的 `set ...ENABLED=0` 被从中间切断，`...ENABLED=0` 后半截 `ent` 被当成命令）。这种构建结果**不可信**，必须等它结束再干净重跑一次。

> 规律：**改 `.bat` 之前先确认没有 build 在跑**；改完用 `data.count(b'\r\n')` 与 `data.count(b'\n')` 比较复核（相等即为纯 CRLF）。

### 3. `app.py --self-test` 一直是假阳性（真 bug）

`--self-test` 原先用 `tk.Tcl().eval("package require Tk")` 探测 Tk，在**源码运行**下必然失败：

```
_tkinter.TclError: couldn't load library ".../tcl/tk8.6/../../bin/tk86t.dll"
```

实测同一个解释器里 `tk.Tcl()`+`package require Tk` **失败**，而 `tk.Tk()` 真实建窗**成功** —— 前者靠 Tcl 自己的相对路径猜 DLL，后者走 tkinter 的正确初始化路径。之前只在**打包版**里看起来"通过"，纯粹是因为 `build_exe.bat` 会把 tcl/tk DLL 复制到 `bin/`。

改为 `_run_self_test()`：真的 `tk.Tk()` + `withdraw()` + `destroy()`，再报一次 GPU 界面依赖是否齐全，逐行打印结论、末尾 `Photo Culler runtime OK` / `INCOMPLETE`，**绝不抛异常**。
- 现在 `.venv-build` 直接 `python app.py --self-test` → `Tkinter 界面可用` / `GPU 界面依赖齐全` / `Photo Culler runtime OK`。
- `test_entry_dispatch.py` 新增 **[6]**：以子进程跑 `--self-test`，断言退出码 0、stdout 含两行结论 + `runtime OK`、stderr **不含 Traceback**。
- 教训：**探测要用"应用真正会做的事"**。用旁路 API（`Tcl()`）去验就只是在验那条旁路。

## 新增 GPU 状态检测 + 可选加速方案（用户需求）

用户要求「检测用户的 GPU 状态（如是否核显、是否独显），并且给出几种 GPU 加速的方案，可选，将选择选项放到菜单栏中」。

### 新增三个模块

- `app_settings.py` —— 用户设置持久化，`%LOCALAPPDATA%\PhotoCuller\settings.json`。**与选片记录分开**（一个损坏的文件不该同时损失两样东西）。读取是全函数（缺失/损坏都回默认，绝不阻塞启动），写入用临时文件 + `os.replace`，未知键原样保留（降级不丢新版本的设置）。
- `gpu_info.py` —— 显卡检测与分类。
- `gpu_accel.py` —— 方案定义与生效机制。

### 检测必须合并三个来源（这是本轮最关键的设计判断）

| 来源 | 提供 |
|---|---|
| 注册表 `HKLM\SYSTEM\...\Class\{4d36e968-...}` | 全部**已安装**适配器（含当前会话未启用的核显）、驱动版本、真实显存（优先 `qwMemorySize`，`MemorySize` 是 DWORD 会在 4GB 饱和） |
| DXGI `CreateDXGIFactory1` → `EnumAdapters1` | 图形栈**当前可用**的适配器 + 软件适配器标志 |
| 实时 OpenGL 上下文 | 预览**实际在用**的渲染器 |

**本机实测就是反例**：注册表给出 `NVIDIA RTX 4050` + `Intel UHD Graphics`（2 块），而 **DXGI 只给出 RTX 4050 + `Microsoft Basic Render Driver`** —— 那块 Intel 核显在当前会话里根本没挂上。**只看 DXGI 会把"有没有核显"答成"没有"。** 所以两者都要，并按归一化名称合并（剥掉大小写与 `(R)`/`(TM)` 噪声，否则同一块卡会被算成两块）。

DXGI 用 ctypes 手写 COM vtable 调用：`EnumAdapters1` 槽位 12（IUnknown 0-2 / IDXGIObject 3-6 / IDXGIFactory 7-11），`GetDesc1` 槽位 10（IDXGIAdapter 7-9）。`DXGI_ADAPTER_FLAG_SOFTWARE = 0x2`。`DXGI_ERROR_NOT_FOUND` 当有符号 `c_long` 是负数，用它做循环终止。

### 核显/独显判定：先归一化名称再匹配

第一版直接在原文上跑正则，两条案例失败：
- `Intel(R) Arc(TM) A770 Graphics`（独显 Arc）判成核显 —— `(TM)` 卡在 `Arc` 和型号之间，`arc\s*[\(\s]*[a-z]?` 匹配不到 `A770`。
- `AMD Radeon(TM) Graphics`（核显）判成 unknown —— `radeon\s+graphics` 要求 Radeon 后紧跟空格，而实际是 `Radeon(TM) Graphics`。

**修法：先剥掉 `(R)/(TM)/(C)/®/™/©` 并压平空白，再跑名称规则。** 商标噪声正好夹在规则要匹配的两个词中间。

规则：NVIDIA 一律独显（Windows 上无 NVIDIA 核显）；Intel 默认核显，带型号的 `arc [ab]\d{3}` 才是独显（`Arc Graphics` 是 Core Ultra 的核显）；AMD `Radeon RX/Pro/VII`、`RX nnnn`、`W|X|Ydddd` 为独显，`Radeon Graphics/Vega N/nnnM` 为核显。名称判不出的才退回显存启发式（专用显存 ≥1GB 视为独显）—— 且**只对 unknown 生效**，已判定的类型绝不被覆盖。`classify()` 是纯函数，15 个案例可无硬件单测。

### 方案与生效机制

| 方案 | 机制 |
|---|---|
| `auto` | 删除本应用的显卡偏好，交回 Windows |
| `discrete` | `HKCU\...\DirectX\UserGpuPreferences` 写 `GpuPreference=2;`（高性能） |
| `integrated` | 同上写 `GpuPreference=1;`（省电） |
| `software` | `PHOTOCULLER_UI=tk` + `PHOTOCULLER_RESAMPLE=cpu`，完全不走 OpenGL |

全部需要重启（环境变量与注册表都在进程启动时被读）。环境变量必须在 `QApplication` 之前设好，所以放在 `app.py` 里 import `qt_ui` **之前**调 `apply_environment()`。

**源码运行拒绝写注册表**：那时进程是共用的 `python.exe`，写进去会把机器上**所有** Python 程序都重定向；`target_executable()` 非 frozen 返回 `None`。方案仍然持久化，但消息明确说明这一部分被跳过（不是假装成功）。

### 两个方案实测后故意不提供（重要）

- **ANGLE / Direct3D**：Qt 6 已从官方构建移除 ANGLE，PySide6 目录里**没有** `libEGL.dll`/`libGLESv2.dll`（已验证），`QT_OPENGL=angle` 只会静默无效。
- **`QT_OPENGL=software`**：这个差点就发布了。原本设计成"兼容模式用 Qt 自带软件 OpenGL"（因为 `opengl32sw.dll` 确实存在）。探针发现该模式下**窗口拿不到 GL 上下文**（`stage.gpu_info` 为 None），而 `auto`/`discrete` 都能拿到 OpenGL 4.6。进一步用裸 `QOpenGLContext` 测出根因：

  | 模式 | 上下文 | GLSL |
  |---|---|---|
  | desktop | OpenGL 4.6 (NVIDIA) | 4.60 |
  | software | OpenGL 3.0 — **Mesa 11.2 llvmpipe** | **1.30** |

  Qt 自带的 `opengl32sw.dll` 是 2016 年的 Mesa 11.2 / GLSL 1.30，VisPy 的场景着色器跑不了。**这个"退路"会把预览弄坏。** 改为切到 Tkinter 界面层 —— 那才是本工程真正的 CPU 通路（`PHOTOCULLER_UI=tk` 已有完整测试覆盖）。

> 教训：**"选项存在"不等于"选项有用"**。两个方案都是先写进去、再实测发现无效/有害才撤掉的。凡是要写进注册表或环境变量的方案，都必须实测它的效果，而不是假定机制成立。

### 界面显示"实际生效"的方案，不只是"已保存"的方案

探针抓到过这个 bug：`apply_environment('software')` 只改了环境变量，面板却显示「方案：自动（推荐）」—— 因为面板读的是 settings。新增 `effective_scheme_id()`（**环境变量优先**，它才是本进程真正在跑的东西），`current_scheme_id()` 仍表示"下次启动用什么"。两者不一致时面板显示 `当前 → 已选（重启后生效）`。

另：`environment()` 只有在方案真的要强制界面层时才输出 `PHOTOCULLER_UI`。若对其它方案输出 `None`，启动时的 `apply_environment` 会把用户手动 export 的 `PHOTOCULLER_UI=tk` 删掉。

### PYZ 符号校验的第三个坑：常量元组会被折叠（本轮踩到）

打包后核验新代码是否进包时，出现了 6 个"MISS"，一度以为代码没打进去。**全部是校验脚本的过滤 bug，代码一直都在。**

- **Python 会把 `return False, "未检测到独立显卡"` 折叠成一个 tuple 常量 `(False, '未检测到独立显卡')`**。字符串藏在元组里，只做 `isinstance(v, str)` 的过滤会整个漏掉。
- 另外两类也是**匹配方式**的问题，不是缺代码：字符串常量常常是**更长的字面量**（正则 `r"(basic\s+render|...|microsoft\s+basic)"`、注册表全路径 `"Software\Microsoft\DirectX\UserGpuPreferences"`、f-string 片段 `'（重启后生效）'`），必须用**子串**匹配而不是集合成员判断。
- **最可靠的定位手段是反汇编**：`dis.dis(fn)` 直接把 `LOAD_CONST` 的真实常量打出来。当时一眼就看到 `LOAD_CONST 2 ((False, '未检测到独立显卡'))`，立刻确认是校验脚本的问题。

> 修正后的遍历要同时：递归进 `co_consts` 里的 code 对象、以及 tuple/frozenset 常量。已写进 `pyside6-vispy-image-viewer` skill。

另外：这轮把 **显卡检测加进了 `--self-test`**（输出适配器清单、独显/核显、当前方案、是否允许写注册表）。这不只是为了给用户诊断信息，更是**唯一能在真实 frozen 环境里验证 ctypes/DXGI/注册表这些"只有打包后才可能出问题"的代码**的手段——静态扫包做不到。打包版实测输出：

```
显示适配器：NVIDIA GeForce RTX 4050 Laptop GPU + Intel(R) UHD Graphics
显卡类型：独显 + 核显（混合显卡）
加速方案：自动（推荐）
Photo Culler runtime OK
```

且打包版**没有**"源码运行，不写入注册表"那行 —— 因为 frozen 时 `target_executable()` 返回真实 exe 路径，说明这条分支判断也是对的。
