### 排掉的两个真实 bug

1. **扫描完成后不建缩略图栏**：`_handle_scan_events` 的非空分支只调 `_show_current`，而 `_show_current` 按设计不重建缩略图栏，导致 `thumbnail_service.request()` 从未被调用、缩略图永远不出来。修法：在 `_show_current` 前补 `_render_thumbnails(center=True)`（`toggle_filter` 同一路径也要）。
2. **过期解码结果覆盖当前图（竞态）**：`_show_current` 命中 JPEG 预览缓存时直接 `_adopt_preview` 并 `return`，**不会 bump loader generation**；于是上一张仍在飞的后台解码会带着"仍然合法"的 generation 到达并被采纳，把 `_current_path_id` 覆写成上一张。Tk 版在 `ui.py:1366` 有 `path_id` 双重校验，Qt 版漏了。修法：`_handle_image_load_events` 里补
   `if path_id != self._current_path_id and path_id != self._loading_path_id: if not (full_flag and path_id == self._loading_full_path_id): return`。

### 经验（踩坑）

- **`except ImportError as e:` 的 `e` 在 except 块结束时会被删除**，闭包/函数体里引用会 `NameError`；必须先在块内拷到另一个变量。

## 缩放流畅度专项（GPU 界面）

用户要求「把图片的缩放功能变得十分流畅」。先做量化基线再动手，`bench_zoom.py`（新）是常驻回归基准。

### 量化基线（改动前）

24MP 照片（6000×4000）下：缩放中位帧 8.2ms（120fps，本身没问题），但**手势中一旦发生全分辨率贴图换入，出现 ~115ms 的尖峰帧**；缩放上限从 4.0 漂到 4.797（超出 `ZOOM_MAX_PIXEL_SCALE`）；全分辨率触发点过早（`fit × 1.08`，而预览纹理此时还没被放大到 1:1）；标记「保留」会把缩放重置。

### 修掉的四个真实缺陷

1. **缩放上限漂移**：`ZoomPlan` 的字段从 `(fit_width, max_magnification)` 改成 `(max_width, min_width)` —— 边界改为**实时矩形宽度**而非锁存的倍率，加 `clamp_target_width()`。`fit_width` / `pixel_scale_limit` / `device_width_provider` 由 `SmoothPanZoomCamera.plan()` 动态推导，视口尺寸变化时 `_on_canvas_resize()` 重新推导并保持当前缩放。现在上限精确停在 4.0000。
2. **全分辨率触发过早**：判定从 `zoom > fit × (1+ZOOM_FULLRES_MARGIN)` 改为 `stage.pixel_zoom() > preview_native_scale() × ZOOM_PREVIEW_NATIVE_MARGIN`（新 `preview_native_scale()` = 贴图 1:1 时的 pixel_zoom）。预览纹理被缩小采样时换更大的贴图毫无收益，却要付 ~47–59ms 的换图代价。
3. **标记「保留」重置缩放**：`toggle_keep` 改调 `_show_current(center=False, reset_zoom=False)`。
4. **手势中 72MB 换图造成尖峰**：把整条全分辨率升级链路（**请求本身** + 解码 + 换图）推到 `_zoom_settled()` 之后 —— 即相机不忙 **且** `seconds_since_zoom_input() >= ZOOM_FULLRES_SETTLE_MS/1000`。单靠 `camera.busy()` 不够：缩放被上限夹住时相机读起来是空闲的，但滚轮还在转。换图本来就得等手势结束，所以感知延迟零成本。

配套：`gc.freeze()` + `gc.set_threshold(20_000, 250, 250)`（`freeze_startup_garbage()`，窗口首次显示后调用）；`ImageLoader.submit(..., want_array=True)` 把 uint8 转换推到解码线程（24MP 的 `np.asarray(pil)` 要 ~54–64ms）。

### 最终实测（24MP，RTX 4050，`bench_zoom.py`）

修正驱动器后（见下）**每个阶段 jank 全为 0**：A/B 对照（全分辨率关/开）max 20.5 / 20.3ms；手势中位 15.5ms；ACTIVE 窗口（24 档）中位 14.8ms、p95 18.6ms、**max 20.0ms**；平移 ~144fps、max 8.8ms、0 jank。中位 ~15ms 正好是 60Hz vsync，说明已经稳定锁帧不掉帧。全分辨率换图落在滚轮停下的空闲尾巴里。`test_gpu_ui.py` 13 步全过。

### 排掉的错误假设（重要，别重复踩）

- **GC 不是元凶**：`gc.callbacks` 监视器显示手势期间 GC 次数为 0；`gc.freeze()` 只是略有帮助。
- **VisPy「惰性初始化」不是元凶**：曾观察到「全程缩放扫描 pass 1 有 2–3 个 65–90ms 尖峰、pass 2/3 完全干净」，一度判断成 `interpolation="cubic", method="subdivide"` 的按尺度惰性构建，差点写一个 warm-up。**把全分辨率升级关掉后，pass 1/2/3 全部平坦（max 7.09ms，0 帧 >15ms）** —— 尖峰全部来自全分辨率换图，没有 warm-up 可做。教训：扫描探针直接设 `camera.rect`，**不会调 `mark_input()`**，于是 `seconds_since_zoom_input()` 永远很大、settle 闸门永远开着，等于绕过了自己刚加的防护；用它测出来的就是「没有闸门时」的行为。
- **绘制成本与缩放级别无关**：`pixel_zoom` 0.3→4.0 强制绘制，中位稳定 6.94–6.96ms。深度放大本身不更贵。

### `bench_zoom.py` 自身的两个测量缺陷（已修）

- **驱动器把每个滚轮档位应用了两次**：它用 `camera.rect.width` 在 `sendEvent` 前后是否变化来判断事件有没有送达。这个判据**永远为真**（看起来像"没送达"），因为相机只记录一个待处理的 log 因子、在定时器里缓动，`sendEvent` 返回时 `rect.width` 根本没变。于是它既发 Qt 事件、又直接调相机 → 每档双倍缩放，把 ACTIVE 窗口的 jank 从 0 放大到 3/122、max 50ms。改为在初始化时用一次性的 spy（包住 `camera._queue_wheel_zoom`）探测送达。修正后同一场景 jank 0/87、max 20.0ms。
- **空闲间隙被当成掉帧**：只给绘制打时间戳，滚轮停下的空闲段会变成一个几百 ms 的"间隔"。`FrameRecorder.report(idle_tail=True)` 现在把 >6 个 vsync 的间隔单独报为 idle gap，不计入 jank。
